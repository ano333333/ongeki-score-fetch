# ADR 001: github-issue-driven-dev を state-workflow-extension 向け client pi 拡張として再定義する

- Status: proposed
- Date: 2026-05-31

## Context

`~/ongeki-score-fetch/.claude/skills/github-issue-driven-dev` は skill として GitHub issue 起点の開発フローを案内している。
これを、`state-workflow-extension` の client extension として再定義したい。

今回の要件は次のとおり。

1. issue 選択
   - `gh` コマンドで優先 issue を 1 件選ぶ
   - 元 skill の選択基準を `userMessage` としてセッションへ投げる
   - issue 本文は workflow 用一時ディレクトリへ書き下ろす
2. plan 作成
   - entry で `userMessage` として plan 作成を指示
   - plan は workflow 用一時ディレクトリへ `PLAN.md` として新規作成
   - ユーザーが手動で次 state へ進める
3. 実装
   - `userMessage` で実装を指示
   - 完了したら `workflow_next` tool で formatter 遷移を確定するよう agent に指示
4. formatter 実行
5. linter 実行
6. linter 失敗
7. test 実行
8. test 失敗
9. レビュー
   - subagent を起動し、一時ディレクトリのレビュー履歴を踏まえてレビュー
10. レビュー対応
11. commit 操作
   - subagent を起動し、機能単位の commit を実行
12. PR 作成
   - subagent を起動し、PR を作成

要求された遷移は以下。

- 1 -> 2: manual
- 2 -> 3: manual
- 3 -> 4: manualOrAgent
- 4 -> 5: auto
- 5 -> 6: failure
- 5 -> 7: success
- 6 -> 4: manualOrAgent
- 7 -> 8: failure
- 7 -> 9: success
- 8 -> 4: manualOrAgent
- 9 -> 10: REJECTED
- 9 -> 11: ACCEPTED
- 10 -> 4: manualOrAgent
- 11 -> 12: auto

また、`state-workflow-extension` の現行 public client API は次を前提にしている。

- 登録は event bus 契約で行う
  - `state-workflow:register-workflow`
  - `state-workflow:register-function-handler`
  - `state-workflow:start-workflow`
- client action は public には次の 3 種のみ
  - `function`
  - `userMessage`
  - `continueSession`
- public client API では `command` action は使わない
- trigger は実質 `success | error | always | manual | manualOrAgent`

## Decision

`github-issue-driven-dev` は、`state-workflow-extension` の standalone client extension として実装する。

base extension の TypeScript を import せず、README に記載された event 名と payload shape を client 側でローカル定義して登録する。

workflow id は `github-issue-driven-dev` とし、12 state を持つ 1 本の workflow とする。

formatter / linter / test / issue 取得 / review / commit / PR 作成はすべて `function` action で表現する。
agent に考えさせたい工程のみ `userMessage` action を使う。

## API 制約に合わせた表現方針

### 1. `failure` は `error` に写像する

要求上の `failure` は、`state-workflow-extension` の trigger では `error` に対応づける。

- linter failure => `error`
- test failure => `error`

### 2. `auto` は `success` の自動遷移で表現する

現行 API に `auto` trigger はないため、
「state action が成功したら即次へ進む」を `success` 遷移で表現する。

したがって以下は `success` 扱いになる。

- 4 -> 5
- 11 -> 12

formatter / linter / review などの function state は、base extension の auto-run により
`waitingManual` または `completed` に達するまで連鎖実行される前提で扱う。

### 3. `ACCEPTED` / `REJECTED` は review handler の成否に写像する

public client API には review 専用 trigger も guard 登録 API もない。
そのため review state は次の contract にする。

- reviewer が `ACCEPTED` を返したら handler success
- reviewer が `REJECTED` を返したら handler error

これにより遷移は以下になる。

- 9 -> 11: `success`
- 9 -> 10: `error`

review 結果の生値は workflow context と一時ディレクトリの review log に保存する。

### 4. formatter / linter / test は `command` ではなく `function`

base extension の public client API では `command` action をサポートしない。
そのため各実行 state は client 側 function handler が `child_process` などでコマンドを実行し、
`ok: true/false` を返す設計にする。

### 5. AI による state 遷移は `manualOrAgent` + `workflow_next` で表現する

base extension の ADR 003 に合わせ、AI に遷移させたい state は `trigger: "manualOrAgent"` を使う。

- `implement` 完了後の formatter 開始
- `fix-linter` 後の formatter 再開
- `fix-test` 後の formatter 再開
- `address-review` 後の formatter 再開

agent が `workflow_next({ transitionId })` を呼ぶと、その turn の終了時に base extension が遷移を確定し、
formatter -> linter -> test -> review の function state を自動で連鎖実行する。

## Workflow definition

state 名は実装向けに次の ID を使う。

1. `select-issue`
2. `create-plan`
3. `implement`
4. `run-formatter`
5. `run-linter`
6. `fix-linter`
7. `run-test`
8. `fix-test`
9. `review`
10. `address-review`
11. `commit`
12. `create-pr`

## State design

### 1. `select-issue`

- action: `function`
- 責務:
  - `gh issue list` / `gh issue view` を使って候補を収集
  - 元 skill と同じ選定基準で 1 件選ぶ
    - 高優先度ラベル
    - assignee なし
    - blocker ラベルなし
    - issue 本文にある依存 issue が open でない
  - workflow 用一時ディレクトリを作る
  - `ISSUE.md` に issue 内容を書き下ろす
  - 選定基準と選定結果を、次 turn で agent が参照できるよう `userMessage` 用文面として context に持つ
- 遷移:
  - `manual` -> `create-plan`

補足:
`select-issue` 自体は deterministic に issue を決める責務を持つ。要件にある「元 skill の選択基準を userMessage としてセッションに投げる」は、この state の handler が次 state 用文面を構築し、`create-plan` の `userMessage` に埋め込むことで満たす。

### 2. `create-plan`

- action: `userMessage`
- 責務:
  - 選んだ issue
  - issue 選定理由
  - `ISSUE.md` の参照先
  - `PLAN.md` を workflow 一時ディレクトリに新規作成すること
  - まだ実装しないこと
  - plan 作成後はユーザーが内容確認し、手動で次に進めること
  を明示して agent に指示する
- 遷移:
  - `manual` -> `implement`

### 3. `implement`

- action: 初期設計は `userMessage`、実装上は follow-up user message を送る `function` handler に置き換え
- 責務:
  - `PLAN.md` に従って実装を進めるよう指示
  - 実装完了後は `workflow_next({ transitionId: "to-run-formatter" })` を呼ぶよう明示
  - 実装中の調査・編集・bash 実行は通常の pi セッションとして進める
  - follow-up 配信により、agent が同一 workflow 文脈のまま `workflow_next` を呼べるようにする
- 遷移:
  - `manualOrAgent` -> `run-formatter`

### 4. `run-formatter`

- action: `function`
- 責務:
  - 設定された formatter command を実行
  - stdout / stderr / exit code を一時ディレクトリに保存
- 遷移:
  - `success` -> `run-linter`

### 5. `run-linter`

- action: `function`
- 責務:
  - 設定された linter command を実行
  - 実行ログを保存
- 遷移:
  - `success` -> `run-test`
  - `error` -> `fix-linter`

### 6. `fix-linter`

- action: `userMessage`
- 責務:
  - 直前の linter エラーを修正するよう agent に指示
  - 修正後は agent が `workflow_next({ transitionId: "retry-formatter-after-lint" })` を呼んで formatter に戻る運用を明示
- 遷移:
  - `manualOrAgent` -> `run-formatter`

### 7. `run-test`

- action: `function`
- 責務:
  - 設定された test command を実行
  - 実行ログを保存
- 遷移:
  - `success` -> `review`
  - `error` -> `fix-test`

### 8. `fix-test`

- action: `userMessage`
- 責務:
  - 直前の test failure 修正を指示
  - 修正後は agent が `workflow_next({ transitionId: "retry-formatter-after-test" })` を呼んで formatter からやり直すことを明示
- 遷移:
  - `manualOrAgent` -> `run-formatter`

### 9. `review`

- action: `function`
- 責務:
  - subagent を起動して diff をレビュー
  - workflow 一時ディレクトリの単一 review 履歴ファイルを読み、継続レビューとして扱う
  - 出力 contract を `ACCEPTED` / `REJECTED` に固定
  - review 結果を `reviews/review.md` へ追記保存
- 遷移:
  - `success` -> `commit`
  - `error` -> `address-review`

### 10. `address-review`

- action: `userMessage`
- 責務:
  - 単一 review 履歴ファイル内の最新 review の指摘修正を agent に指示
  - 修正内容も同じ review 履歴ファイルへ追記する運用を明示
  - 修正後は agent が `workflow_next({ transitionId: "retry-formatter-after-review" })` を呼んで formatter からやり直す運用を明示
- 遷移:
  - `manualOrAgent` -> `run-formatter`

### 11. `commit`

- action: `function`
- 責務:
  - subagent を起動し、変更を機能単位で stage / commit
  - commit 結果を `COMMITS.md` などへ保存
- 遷移:
  - `success` -> `create-pr`

### 12. `create-pr`

- action: `function`
- 責務:
  - subagent を起動し PR 本文を作成
  - `gh pr create` を実行
  - PR URL を保存
- 遷移:
  - 遷移なし。完了 state

## Workflow temp directory

初版では、固定の作業ディレクトリを使う。

```txt
.pi/workflows/github-issue-driven-dev/current/
```

run ごとの履歴管理は後続課題とし、まずは state 間で安定参照できる固定パスを優先する。

最低限保存するもの:

- `ISSUE.md`
- `PLAN.md`
- `formatter.log`
- `linter.log`
- `test.log`
- `reviews/review.md`
- `COMMITS.md`
- `PR.md`
- `meta.json`

`meta.json` には少なくとも以下を保持する。

- workflow id
- issue number / repo
- selected at
- commands
- current artifact paths
- latest review result
- pr url

## Client registration contract

client extension では base extension を import せず、次をローカル定義する。

- `REGISTER_WORKFLOW_EVENT = "state-workflow:register-workflow"`
- `REGISTER_FUNCTION_HANDLER_EVENT = "state-workflow:register-function-handler"`
- `START_WORKFLOW_EVENT = "state-workflow:start-workflow"`

また、base より client が先に load される可能性があるため、登録は

- extension load 時
- `session_start` 時

の両方で再送する。

## Commands

client 独自に少なくとも次を持つ。

- `/issue-driven-dev-start`
  - client workflow を開始する
  - 実装は `state-workflow:start-workflow` を emit して base に委譲する
- `/issue-driven-dev-open-dir`
  - 現在の workflow 一時ディレクトリを通知する

workflow 進行自体は base extension の既存 command を使う。

- `/workflow-next`
- `/workflow-choose <transitionId>`
- `/workflow-status`
- `/workflow-abort`

## Configuration

project ごとに次の設定を client extension 側で持つ。

- `repo`: `owner/name` 省略時は `origin` から推定
- `priorityOrder`: 例 `priority-0,priority-1,priority-2,priority-3`
- `formatterCommand`
- `linterCommand`
- `testCommand`
- `workingDirectory`
- `reviewSubagent`
- `commitSubagent`
- `prSubagent`

## Consequences

### Benefits

- `state-workflow-extension` の現行 public API だけで表現できる
- deterministic な工程と agentic な工程を分離できる
- review rejection / lint failure / test failure を明示的なループとして扱える
- issue, plan, review, commit, PR の監査情報を一時ディレクトリに残せる

### Costs

- `failure`, `REJECTED`, `ACCEPTED`, `auto` は API 上の trigger 名そのままでは使えない
- `command` action が public API にないため、formatter/linter/test は function handler 実装が必要
- review 分岐は trigger ではなく handler contract に依存する
