# ADR 002: github-issue-driven-dev の現行 workflow 構成を明文化する

- Status: accepted
- Date: 2026-06-11

## Context

`github-issue-driven-dev` は、`state-workflow-extension` 向け client extension として導入した後、実運用に合わせて state と handler の責務を整理してきた。

初期 ADR で示した 12 state 構成から、PR 監視の待機とユーザー確認を独立 state として切り出し、review / commit / PR / PR monitor 周辺の補助処理も分割した。

一方で、base extension 側の public client API に guard 登録機構はなく、workflow の詳細分岐は success / error / manual / manualOrAgent に制限される。
そのため、PR 監視後の細かな分岐や handler の責務境界を明文化しておかないと、将来の変更で設計意図が失われやすい。

加えて、repo ごとの差分が出やすい設定値をコードに固定したままでは、運用調整のたびに extension 自体の変更が必要になる。

## Decision

`github-issue-driven-dev` の現行構成は、15 state の workflow と、それを支える分割モジュール群を基本設計として維持する。

guard API がない制約は受け入れ、PR 監視後の詳細分岐は `meta.json` に保存する next-action で表現する。

function handler の契約は「正常 return で success 遷移、throw で error 遷移」とし、意図的な error 遷移を表すために `WorkflowErrorTransition` を使う。

repo / issue 選定 / agent 名 / verification 実行対象 / PR monitor 待機時間は、workflow 配下の `config.json` で任意に上書きできるようにする。
`config.json` が無い場合の挙動は既定値をそのまま使う。

## Workflow definition

state 名は次の 15 個を使う。

1. `select-issue`
2. `create-plan`
3. `implement`
4. `run-formatter`
5. `run-linter`
6. `fix-linter`
7. `run-test`
8. `fix-test`
9. `review`
10. `address-review`
11. `commit`
12. `create-pr`
13. `monitor-pr`
14. `wait-pr-monitor`
15. `pr-user-confirm`

`monitor-pr` は PR 状態の取得と review 要否判定を担い、`wait-pr-monitor` は待機とユーザー確認分岐の接着だけを担う。
これにより、PR 状態判定と workflow 再実行制御を分離する。

## API 制約に合わせた表現方針

### 1. guard 分岐は `meta.json` の next-action で表現する

public client API には guard を差し込む仕組みがない。
そのため `monitor-pr` handler は PR 状態を見て `prMonitorNextAction` を `meta.json` に記録し、後続の `wait-pr-monitor` state がその値を見て振る舞う。

具体的には次を使う。

- `WAIT`
- `USER_CONFIRM`
- `COMPLETED`
- `REVIEW_REJECTED`

`WAIT` は待機後の再実行、`USER_CONFIRM` はユーザー確認待ち、`COMPLETED` は merge 済み、`REVIEW_REJECTED` は review フローへの差し戻しを表す。

### 2. handler の throw を error 遷移として扱う

workflow には個別の判定 trigger を増やさない。
その代わり、handler が正常終了した場合だけ success 遷移させ、再試行や差し戻しが必要な場合は throw で error 遷移させる。

`WorkflowErrorTransition` は、単なる異常終了ではなく workflow 上の意図した error 遷移であることをコード上で明示するために導入する。

この契約は次の箇所で使う。

- linter / test failure
- review rejected
- PR monitor による review 差し戻し
- PR monitor wait からの再試行

### 3. agent への指示は follow-up user message または subagent に限定する

実装、linter 修正、test 修正、review 指摘対応は follow-up user message を使う。
review / commit / PR 作成 / PR feedback judgement は subagent 委譲を使う。

これにより、base extension との通信経路を event bus と function handler 契約に限定したまま、agent に考えさせたい工程だけを分離する。

## Module structure

実装は責務ごとに分割する。

- `handlers/`: workflow state に直接対応する entry point
- `pr/`: PR view、feedback fingerprint、auto-reply、judgement、markdown 生成
- `review-history.ts`: `reviews/review.md` の単一履歴ファイル管理
- `prompts.ts`: follow-up user message の文面生成
- `project-config.ts`: `config.json` 読み込みと既定値マージ
- `workflow-transition.ts`: error 遷移の明示用エラー型
- `git.ts`: branch / push 補助

state に 1 対 1 で対応する handler だけを `handlers/` に置き、補助ロジックは横断モジュールへ逃がす。
これにより、state 定義・handler 契約・補助処理の責務境界を維持しやすくする。

## Configuration policy

プロジェクト固有の調整値は `WORKFLOW_ROOT/config.json` で上書きできるようにする。

対象は次のとおり。

- `repo`
- `priorityOrder`
- `issueLimit`
- `reviewAgent`
- `commitAgent`
- `prAgent`
- `prMonitorAgent`
- `formatterTargets`
- `linterTargets`
- `testTargets`
- `prMonitorWaitMs`

読み込みは shallow merge のみを行い、ランタイムバリデーションは行わない。
壊れた JSON の扱いは `readJson` の挙動に委ねる。

## Consequences

現行の workflow は、public client API の制約を破らずに PR 監視を含む 15 state 構成を維持できる。

next-action を `meta.json` に残すため、PR 監視の分岐理由を後から追跡しやすい。

一方で、分岐条件は型安全な workflow 定義ではなく metadata に表現されるため、`monitor-pr` と `wait-pr-monitor` の契約を変更する際は両者を同時に見直す必要がある。

`config.json` により repo ごとの運用差分は吸収しやすくなるが、設定値は実行時検証しないため、不正な JSON や不整合な型はそのまま実行時エラーになりうる。
